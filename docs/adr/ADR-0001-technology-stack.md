# ADR-0001: Technology stack

**Status:** accepted · 10 Nov 2026

## Context

ANCHOR must:
- run fully offline on shared COTS crew laptops and tablets;
- be deterministic, so that replaying the log reproduces every output (I5);
- isolate a safety kernel that is written twice, independently (N-version, DESIGN_PAPER §5.2);
- compute non-trivial statistics: Student-t CDF, normal quantiles, conjugate Bayesian updates, CUSUM, block bootstrap;
- present a touch UI.

Toolchain available: Rust 1.96, Node 22, Python 3.11 with numpy/scipy.

## Options considered

| Option | For | Against |
|---|---|---|
| **A. TypeScript everywhere** (core + UI), Python for analysis | One language; the browser is the runtime; fastest UI iteration | Dynamic runtime with GC; weak guarantees for a safety kernel; numerics written in a language without integer/overflow discipline; N-version diversity would be only "same language, different author" |
| **B. Rust core (native + WASM), TypeScript UI, Python oracle** | Memory safety without GC; explicit error handling (`Result`, no exceptions), close to Power-of-Ten discipline; a native binary for laptops and WASM for browsers from one source; strong types for units and fixed-point values; compiled languages are flight-software practice (NASA cFS is C, and Rust is increasingly used) | Two-language interop (WASM boundary); longer build; the WASM target must be installed |
| **C. Python core + web server** | Richest scientific stack | Needs a Python runtime and a server process on crew devices; non-deterministic dependency surface; poor fit for an offline tablet |
| **D. C core** (as RAKIA) | Maximal portability to flight computers | Memory-safety burden, which moves risk into the very component that must be most trustworthy |

## Decision

**Option B.**
- **Rust core** (`core/`): event log, safety kernel A, numerics, personal model, detection.
- **TypeScript** for safety kernel B (`kernel-b/`) and the UI.
- **Python** (`oracle/`) as an independent reference implementation of every numerical routine, and for the ANCHOR-Bench generator.

## Rationale (the deciding arguments)

1. **N-version diversity is real only across languages, compilers and runtimes.** Kernel A (Rust, compiled) and kernel B (TypeScript, JIT) share no code, no compiler and no standard library. A common-mode error would require the same logical mistake made twice, independently, against one written specification.
2. **A numerical oracle in a third ecosystem.** scipy's special functions are mature and widely used. Every Rust numeric routine is checked against test vectors generated by scipy, so we do not trust our own maths.
3. **Determinism.** All derived state is computed by one implementation (Rust). Floating-point results are therefore reproducible across replays on the same build. The kernels compare only *integer fixed-point* inputs against integer thresholds, so cross-language floating-point differences cannot reach a safety decision.
4. **Option C is excluded by the operating environment, and option D by the risk profile.**

## Consequences

- Records carry integer fixed-point values, never floats (see ADR-0002).
- Dependencies are kept minimal, pinned and justified one by one. The only runtime crate at start is `sha2` (RustCrypto), so that we do not hand-write a cryptographic hash.
- WASM packaging (`wasm32-unknown-unknown`) is added when the UI starts. Until then the core is developed and tested natively with `cargo test`.
